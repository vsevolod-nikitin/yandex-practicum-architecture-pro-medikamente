# Задание 5. Разработка cutover-плана

## 1. Исходное состояние

Сейчас компания Medikamente использует следующую ИТ-инфраструктуру:

- данные ведутся в файлах Excel;
- 1С работает в файловом режиме;
- все компоненты размещены на одном физическом сервере;
- централизованная база данных и API отсутствуют;
- бизнес-процессы не автоматизированы.

По мере роста компании эти ограничения становятся все заметнее: систему сложно масштабировать, возрастает вероятность ошибок, возникают риски для безопасности данных, а подключение внешних сервисов затруднено.

### Целевое состояние

В результате миграции планируется сформировать современную архитектуру, включающую:

- единую базу данных на PostgreSQL;
- набор взаимодействующих микросервисов;
- интеграции через API;
- портал для клиентов;
- платформу для аналитики.

## 2. Стратегия перехода

Для миграции рассмотрены три подхода:

| Стратегия | Суть подхода | Основное ограничение |
| --- | --- | --- |
| High-level design | Создать новую архитектуру целиком и затем перейти на нее | Высокий риск перехода |
| Parallel run | На время запустить старую и новую системы параллельно | Требуется синхронизировать данные |
| Branch by abstraction | Переносить функциональность постепенно, сохраняя совместимость | Потребуются изменения в архитектуре |

### Выбранный подход: Parallel run

Параллельная эксплуатация систем позволит:

- снизить вероятность остановки бизнес-процессов;
- проверить новую систему в реальных условиях;
- переводить пользователей поэтапно;
- при необходимости оперативно вернуться к прежней системе.

При этом нужно учитывать дополнительные затраты на поддержку двух систем, повышенную нагрузку на инфраструктуру и необходимость поддерживать данные согласованными.

## 3. Этапы миграции и переключения

Переход предлагается выполнить последовательно:

| Этап | Работы | Основные задачи | Ответственные | Срок | Риск и способ снижения |
| --- | --- | --- | --- | --- | --- |
| 1 | Подготовка инфраструктуры | Развернуть Kubernetes и PostgreSQL | DevOps, архитектор | 2 недели | Ошибки конфигурации — предварительно проверить настройки в тестовой среде |
| 2 | Создание новой архитектуры | Разработать микросервисы | Backend-команда | 4 недели | Архитектурные ошибки — проводить code review |
| 3 | Перенос данных | Перенести данные из Excel и 1С | DBA | 2 недели | Потеря данных — создать резервные копии |
| 4 | Подключение интеграций | Настроить API лаборатории и платежных сервисов | Backend-команда | 2 недели | Нестабильность API — проверить интеграции до запуска |
| 5 | Параллельный запуск | Обеспечить одновременную работу старой и новой систем | DevOps | 3 недели | Расхождение данных — контролировать синхронизацию |
| 6 | Перевод пользователей | Постепенно подключить сотрудников к новой системе | ИТ-отдел | 2 недели | Ошибки при работе — организовать обучение |
| 7 | Наблюдение за системой | Отслеживать производительность и стабильность | DevOps | Постоянно | Снижение производительности — контролировать метрики и реагировать на отклонения |
| 8 | Завершение перехода | Отключить старую систему после подтверждения готовности новой | CTO | 1 неделя | Критические ошибки — сохранить возможность отката |

## 4. Важные аспекты перехода

### Перенос данных

При переносе возможны потеря информации и несовпадение форматов. Чтобы снизить эти риски, необходимо заранее сделать резервные копии и проверить целостность перенесенных данных.

### Согласованность систем

Пока обе системы работают параллельно, данные в них должны оставаться согласованными. Для синхронизации можно применять ETL-процессы и событийный обмен данными.

### Производительность

Новая архитектура может столкнуться с задержками в сети и дополнительными расходами времени на взаимодействие микросервисов. До перехода следует провести нагрузочное тестирование, а после запуска — постоянно отслеживать состояние системы.

## 5. Участники и зоны ответственности

| Роль | Зона ответственности |
| --- | --- |
| Архитектор | Проектирование целевой архитектуры |
| DevOps-инженер | Подготовка инфраструктуры и развертывание системы |
| Backend-команда | Разработка сервисов |
| DBA | Перенос данных |
| QA-инженер | Проверка качества и тестирование системы |
| CTO | Принятие итогового решения о переключении |

## 6. Основные риски

| Риск | Вероятность | Последствия | Меры снижения |
| --- | --- | --- | --- |
| Потеря данных | Средняя | Критические | Регулярно создавать резервные копии |
| Снижение производительности | Средняя | Высокие | Мониторить систему |
| Сбои интеграций | Высокая | Средние | Тестировать API |
| Ошибки пользователей | Высокая | Низкие | Обучить сотрудников |

## 7. План отката

Если новая система работает нестабильно, следует:

1. остановить ее работу;
2. вернуть пользователей на прежнюю систему;
3. восстановить данные из резервной копии;
4. проанализировать причины сбоя.

## 8. Мониторинг после перехода

Для наблюдения за системой можно использовать Prometheus, Grafana, VictoriaMetrics и ELK Stack.

В ходе мониторинга следует отслеживать:

- нагрузку на сервисы;
- количество и характер ошибок API;
- время ответа системы.
